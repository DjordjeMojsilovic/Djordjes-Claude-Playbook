# House rules

These apply to every project. My instructions in the chat always win over this file.

## How to work
- Think before acting. Read the existing files before you write code.
- Keep the answer short and the reasoning thorough. No flattering openers, no closing fluff.
- Edit instead of rewriting whole files. Keep solutions simple and direct.
- Don't re-read a file you already read unless it may have changed. Skip files over 100 KB unless I ask for them.
- When the goal is clear, act. Don't debate options with me. Fast is not sloppy: finish the job properly.
- When a session gets long, suggest `/compact`. When I switch to an unrelated task, suggest a new session.

## What I've learned to insist on
- "Don't touch X" means zero diff on X. Check the diff before you say you're done.
- Existing typography, navigation and animations stay as they are unless I say otherwise. After every PR, check for regressions.
- "Done" needs proof: it's live, it compiled, a screenshot, or a log. Test before you say it works.
- If a word can mean two things, pin it to the example I showed you. If there's no example, ask for one.
- Point out requirements from the material yourself, before I find them. Justify every score or rating you give.
- Experiments go in a branch or a prototype folder, so rolling back is one command.
